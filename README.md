# Margin Map

Transparent profitability, discount, and scenario analytics over Superstore sales — from raw transactions to a live dashboard served by one public URL.

Deployment pending — follow `docs/DEPLOYMENT.md` to deploy; the Live Demo URL is recorded here only after it is verified.

## Project Overview

Margin Map moves beyond revenue-based reporting to explain where profitable and unprofitable revenue is generated. It builds a reproducible analytical pipeline — Python data preparation, modeled cost economics, discount-band analysis, hypothetical scenario sensitivity, variance reporting, order-grain readings, SQLite delivery, a read-only FastAPI backend, and a React dashboard — all reconciled to the same frozen figures.

## Business Problem

Revenue growth does not always translate into stronger profitability. Discounting, product economics, and downstream service costs can materially affect the contribution generated by each sale. Margin Map addresses this by building a transparent profitability model from transactional sales data and extending it toward cost-to-serve and pricing analytics.

The analysis focuses on:

- Revenue and gross margin performance
- Product-level profitability
- Customer and regional profitability
- Discount impact on margins
- Cost-to-serve drivers
- Identification of margin erosion
- Pricing and portfolio decision support

## Analytical Approach

The project establishes a reproducible financial model using transactional sales data.

Key financial measures include:

- **Net Revenue** – recorded sales revenue after discount
- **Modeled COGS** – estimated cost of goods sold using documented industry gross-margin benchmarks
- **Gross Profit** – Net Revenue minus Modeled COGS
- **Gross Margin %** – Gross Profit as a percentage of Net Revenue
- **Cost-to-Serve** – OBSERVED freight allocated to line/order grain; returns and support scenarios are OFF (0) in the baseline, meaning excluded — never actual zero cost. See `docs/COST_TO_SERVE_MODEL.md`.
- **Contribution Profit** – OBSERVED net revenue minus MODELED COGS minus cost-to-serve (freight only in baseline)
- **Contribution Margin %** – contribution profit as a percentage of revenue
- **Discount Leakage** – difference between estimated gross revenue and recorded net revenue

All financial definitions and calculation rules are documented in `docs/FINANCIAL_MODEL.md`.

## COGS Methodology

Because historical COGS is not available in the source dataset, MarginMap uses a documented **modeled COGS methodology** rather than treating the source Profit field as accounting COGS.

Gross-margin benchmarks are assigned across the 17 product sub-categories using available industry references. Where direct sub-category evidence is unavailable, category-level benchmark assumptions are used and explicitly identified. All 1,894 analytical products are covered with zero dependency on the quarantined Profit field (independence-checked).

The resulting financial model estimates (point estimates; ±5pp sensitivity band in parentheses):

- Revenue: **$2.30M**
- Modeled COGS: **$1.49M**
- Modeled Gross Profit: **$803.29K** ($688K–$918K under ±5pp)
- Modeled Gross Margin: **34.97%** (29.97%–39.97% under ±5pp; band width only — see `docs/COGS_SENSITIVITY.md` for structural limitations)

The modeled COGS should therefore be interpreted as an **analytical estimate**, not historical accounting COGS.

Detailed methodology and source documentation are available in:

- `docs/COGS_MODEL.md`
- `docs/SUBCATEGORY_BENCHMARK_METHODOLOGY.md`
- `docs/MODELED_COGS_VALIDATION.md`
- `docs/COGS_SENSITIVITY.md`

## Returns Treatment

Returns are flag-only: 296 returned order IDs plus 1 UNKNOWN unmapped return order, carried as order-level status for filtering. No refund amounts, dates, quantities, reasons, or transactions exist in the source, so no refund reversal or return-handling economics are fabricated. UNKNOWN remains UNKNOWN. Return handling OFF means excluded — never actual zero cost.

## Scenario Methodology

Frozen replacement-rate methodology. Genuine scenarios are the lower-rate (0.10, below-mean) + median (0.20) pair bracketing the mean (0.1562); 0.20 is the observed median discount, so the pair is not symmetric sensitivity and no 0.30 rate is added for symmetry. Identity controls at ±0.00 verify zero variance. Quantity is held constant at observed values, COGS uses the frozen modeled percentage, freight passes through observed values, the baseline stays immutable, and variance equals hypothetical minus baseline:

```text
gross             = sales / (1 - baseline_discount)
hypothetical_net  = gross * (1 - replacement_discount)
hypothetical_cogs = hypothetical_net * frozen_cogs_pct
hypothetical_CTS  = observed order freight
variance          = hypothetical - baseline
```

Every figure is hypothetical arithmetic sensitivity under stated assumptions — not a forecast.

## CTS / Freight Methodology

Observed freight-based methodology. Source `Dataset 1 Apoorva.zip → Global_Superstore2.csv → Market == US`: 9,994 rows, freight $238,173.79. No invented carrier economics and no invented return-freight recovery. Two ambiguous lines preserve NULL freight (flagged); their order total is authoritative at order grain.

## Known Limitations

- COGS is an assumption-based estimate restated from external benchmarks (confidence limits documented).
- Returns are flag-only (no refund economics).
- Scenarios hold quantity constant and carry no demand response.
- Universal pp-shift scenarios are documented as unshippable under the no-clipping contract.
- Freight join uses a hardened normalized-float signature (no stable shared source identifier exists).
- PBIP report uses absolute paths by tool design.
- Touch, screen-reader, and non-Chromium validation have documented gaps.
- Orders `count` reflects the returned page (backend envelope behavior).
- Production bundle is ~673 KB minified (Recharts included).

The transactional grain is one product line within an order.

The source dataset contains sales, quantity, discount, product, customer, geographic, and order information. It does not contain historical COGS, freight cost, return cost, support cost, sales channel, or product weight.

## Data Quality & Governance

Data quality checks are incorporated into the preparation pipeline to ensure that the analytical model remains reproducible and auditable.

Key controls include:

- Source-to-output row reconciliation
- Duplicate and uniqueness checks
- Data type validation
- Revenue reconciliation
- Product identity validation
- Missing-value checks
- Product ID conflict detection
- Deterministic pipeline execution
- Financial calculation validation

The source `Profit` field is retained for reference but is quarantined because its underlying calculation is not established sufficiently to use it as authoritative COGS or profitability.

Product identity is handled using:

`Product ID + Product Name`

This prevents conflicting product-name mappings from being incorrectly merged into a single analytical product.
